# Cross-platform installer

<product-contract>

## Product Requirements

Issue #86: one user-facing installer per platform that installs any combination of Gateway, Workshop, and the speech-to-text library, with CI proving each component installs and runs on each platform.

- Problem and users:
  - Windows users already get this: the NSIS installer (`crates/workshop/desktop/installer.nsi`) has a license page, custom header and sidebar graphics, and a components page (line 428) with Workshop, Gateway, and STT. But STT installs nothing: its section is empty (lines 813 to 816) and only writes the `InstallSTT` registry value that the gateway's first-run config reads (`crates/gateway/app/src/boot.rs`, lines 33 to 78). The gateway downloads the whisper library and the configured models at boot instead, when the boot command's speech load runs (`load_speech`, `crates/gateway/app/src/boot_load.rs`, line 345).
  - macOS users get a drag-install DMG whose `.app` always embeds the gateway (`bundle.externalBin`, `crates/workshop/desktop/tauri.conf.json`, line 13). No license, no components, no Gateway-only install, and the gateway's Launch at Login is disabled because the gateway is not its bundle's principal executable (`LoginService`, `crates/gateway/app/src/tray/macos.rs`, line 374).
  - Linux users get a `.deb` and an AppImage, both always carrying the gateway, with no GUI and no component choice. A Gateway-only path exists only as cargo-dist's Linux tarball and shell installer.
  - Maintainers run four overlapping build pipelines: `release-workshop.yml`, `nightly.yml` (the same matrix, untested), `workshop-installer-smoke.yml` (a debug NSIS compile), and cargo-dist (`promptforge-gateway-v-release.yml`, `gateway-release-test.yml`, `dist-ci/build-setup.yml`, `dist-workspace.toml`), whose plan job runs on every pull request. The gateway sidecar staging exists three times (inline bash in two workflows, `tools/stage-gateway-sidecar.mjs`). The release test installs only the default all-components selection, and nothing tests STT.
- Goals:
  - Windows: the existing NSIS installer, with STT installing the library.
  - macOS and Linux: a Qt Installer Framework wizard with a license page, PromptForge graphics, and the same three components.
  - Any combination installs and works: Workshop alone attaches to a configured remote gateway; Gateway alone runs its tray and Settings page; STT requires Gateway.
  - The gateway stays current on every install shape: it updates itself from the same `latest.json`, Workshop asks it to when both are installed, and NSIS updates all components when Workshop drives a Windows update.
  - One workflow builds, tests, and publishes; the gateway-only cargo-dist build is gone, so pull requests no longer run its plan job.
- Non-goals:
  - A headless or CLI install path for users (Qt IFW's unattended mode and the NSIS `/COMPONENTS=` switch exist for CI; they are not documented as user features).
  - Pacman, RPM, Flatpak, Homebrew, or a `.deb`.
  - Platform code signing and notarization; status unchanged (absent).
- Success criteria:
  - A `v*` tag publishes one release holding the Windows `-setup.exe`, the macOS ARM and Intel installers, and the Linux x86_64 and ARM64 installers, plus `SHA256SUMS` and `latest.json`, only after every install test passes.
  - On each of the five platforms CI installs four selections (all three; Workshop only; Gateway only; Gateway and STT), and each test checks exactly the components selected are present, each present component runs, and each absent one is absent.
  - An installed Workshop and gateway at 0.N, offered 0.N+1, both end at 0.N+1 on every platform, and a Gateway-only tray install at 0.N shows the 0.N+1 notice within 24 hours and, when the user chooses Update, ends at 0.N+1 on every platform.

## Functional Specification

- Components:
  - **Workshop**: the desktop app. Windows: `promptforge-workshop.exe` in the install dir. macOS: `PromptForge.app`. Linux: `PromptForge.AppImage`.
  - **Gateway**: Windows: `promptforge-gateway.exe` beside Workshop (unchanged). macOS: `PromptForge Gateway.app`, an `LSUIElement` bundle whose principal executable is `promptforge-gateway`. Linux: the `promptforge-gateway` binary.
  - **Speech to Text**: requires Gateway. Per-user: `init` runs as the installing user and provisions into that user's profile, as the gateway's config and artifact store already are, so other accounts on the machine provision STT on first use. Installs the platform's whisper runtime and the STT models by running the installed gateway's `init` subcommand, which runs the same provisioning the gateway's boot runs (see First-run initialization), with the pinned SHA256 checks it already performs, so boot then finds the cached files. On a fresh install the models are the generated config's pair, `whisper-base-en` and `whisper-small-en` (`STT_MODELS_TOML`, `crates/gateway/app/src/boot.rs`, lines 323 to 337, about 600 MB together), so STT works offline right after install. The runtime adds about 0.9 to 3 MB for a CPU build, or 524 MB (Windows) and 743 MB (Linux x86_64) for a CUDA build.
- Install layout:
  - Windows: unchanged (NSIS in Tauri's default `currentUser` mode, one directory).
  - macOS: default target `@ApplicationsDir@/PromptForge/` holding the two bundles and Qt IFW's `maintenancetool.app`.
  - Linux: default target `@HomeDir@/PromptForge/` holding the AppImage, the gateway, and the maintenance tool; desktop entries for Workshop and Gateway Settings in `~/.local/share/applications`.
- Peer discovery: Workshop finds the gateway it launches, and the gateway tray finds the Workshop it opens, through one lookup that knows the three layouts in both directions:
  - Beside the executable (Windows, development builds).
  - macOS: sibling bundles in the directory holding the running `.app` (`PromptForge.app`, `PromptForge Gateway.app`).
  - Linux: Workshop finds `promptforge-gateway` in the directory holding `$APPIMAGE`; the gateway finds `PromptForge.AppImage` by name in its own directory, never through an inherited `$APPIMAGE`, so a gateway started from its desktop entry or at login finds Workshop too.
  - Attach through the gateway discovery file is unchanged.
- Gateway spawn environment: a gateway that Workshop launches from inside the AppImage starts without the AppImage's variables: `APPIMAGE`, `APPDIR`, `ARGV0`, `OWD`, and any search-path variable (`LD_LIBRARY_PATH`, `PATH`, `XDG_DATA_DIRS`, `GIO_*`, `GDK_*`, `GST_*`) entries that point under `$APPDIR` are removed. The gateway is a separate install and must not load libraries from a mount that disappears when Workshop exits.
- First-run initialization: `promptforge-gateway init [--no-stt]` writes the default config when none exists (the same generation `boot.rs` runs today, `generate_default`, line 263) and, without `--no-stt`, provisions the whisper library and every `[[stt_model]]` the config in effect declares. With a config present it changes no config and still provisions what that config declares; when speech is requested and the selected profile declares no `[[stt_model]]`, as in a config generated under `--no-stt`, it fails naming the config and the profile instead of reporting success. Its failure message names the missing piece (network, digest mismatch, unwritable directory) with required versus actual, and it exits nonzero.
  - Provisioning reuses the boot's. Today, after the bind, the boot command loads the active profile and `load_speech` runs (`crates/gateway/app/src/boot_load.rs`, lines 86 and 345; enqueued in `crates/gateway/app/src/runner/thread.rs`, lines 271 to 281). It calls gateway-stt's `prepare` (`crates/gateway/stt/api/src/artifacts.rs`, line 43, `pub(crate)` today), which provisions the library through `ArtifactStore::provision_whisper_library_with_cancellation` (`crates/gateway/local/src/artifacts/install.rs`, line 132) and each model through the artifact store's `ensure_model` family (`crates/gateway/local/src/artifacts.rs`, line 152), and starts no decoder. `init` calls `prepare` through a new public entry point, so the install picks the backend boot would: `[stt] whisper_backend` (`WhisperBackend`, `crates/gateway/config/src/config/stt.rs`, line 140), and under `auto` the GPU, driver, `CUDA_VISIBLE_DEVICES`, and libstdc++ probe (`auto_whisper_backend`, `crates/gateway/local/src/artifacts/assets/whisper_auto.rs`, line 20). The `auto` probe therefore runs at install; a later GPU or driver change makes the next boot download the other build, which is accepted.
  - `init` is gated on the gateway's optional `local` and `stt` Cargo features (`crates/gateway/app/Cargo.toml`, lines 129 and 140), both default and present in every installer build.
  - The installers run it as the installing user once Gateway is selected, and wait for it. NSIS uses `nsExec::ExecToLog`: the install is `currentUser`, so the installer already runs as that user; it waits, returns the exit code, opens no console window, and streams `init`'s progress lines into the details pane (`nsis_tauri_utils::RunAsUser` launches through the shell and returns neither a wait nor an exit code). Qt IFW uses a synchronous `Execute` operation, which streams the command's output into Show Details (Step 6). Both run `init` with the install directory as the working directory: without `--config`, `init` discovers a config beside the executable, then in the working directory, then in the profile, so the directory the installer was launched from must not steer it. The STT component's description and the ready-to-install page state the download and its size (about 600 MB of models, plus up to 743 MB for a CUDA runtime); in Qt IFW the STT component's display name carries the size, as the NSIS section title does. IFW 4.11 has no script API for status text before the `Execute` operation, so none is added (Step 6).
  - `init` prints progress lines (artifact, bytes done of total), fed by the artifact store's existing progress activity, at most one per second and at most one per 5% of an artifact, plus a line when each artifact starts and finishes, so the NSIS details pane and CI logs show movement without flooding.
  - In NSIS a nonzero exit is shown on the finish page and leaves Gateway installed. In Qt IFW it opens the installer's error box naming the command: Retry runs it again, Ignore finishes with Gateway installed, and Cancel rolls back the installation (Step 6).
  - Update installs never run `init`: NSIS skips it under `/UPDATE` (read in `.onInit`, `installer.nsi`, line 566), so a passive auto-update never downloads the STT runtime. Every existing Windows user has `STT=1` persisted from when the checkbox was a config gate, and passive mode would hide a failed download.
- Updates:
  - Workshop: unchanged. The Tauri updater (endpoint and public key at `tauri.conf.json` lines 39 and 41; supported except on Linux without a non-empty `APPIMAGE`, `desktop_update_supported`, `crates/workshop/desktop/src/main.rs`, lines 114 to 120) replaces the `.app` or AppImage on macOS and Linux, and runs the NSIS installer in passive mode with the persisted selection on Windows.
  - Gateway self-update: the gateway reads the same `workshop-latest/latest.json` the Workshop updater polls and compares the entry for its platform against its own version. The URL is a constant, overridable through `PROMPTFORGE_UPDATE_URL`, matching the existing `PROMPTFORGE_MODELS_SHEET_URL` convention; the signature check below is what makes the override safe, and only a newer version is ever applied.
    - macOS and Linux read the gateway targets (`darwin-aarch64-gateway`, `darwin-x86_64-gateway`, `linux-x86_64-gateway`, `linux-aarch64-gateway`): a signed archive of the gateway bundle or binary.
    - Windows reads `windows-x86_64`, the NSIS setup, and applies only when no Workshop is installed beside the gateway (peer lookup). With Workshop present, Workshop's updater owns Windows updates, because NSIS updates every installed component and two concurrent NSIS runs must not happen; the route then answers that updates come from Workshop on this install.
  - Verification: the download's minisign signature is checked with the `minisign-verify` crate (already in `Cargo.lock` through `tauri-plugin-updater`) against the release public key the gateway embeds, the same key as `plugins.updater.pubkey` in `tauri.conf.json`. A missing or failing signature refuses the update and names the platform key and the reason.
  - Apply on macOS and Linux:
    1. Download into a staging directory beside the install, on the same filesystem; verify; extract; run the staged binary's `--version` and require the advertised version.
    2. Swap by rename while running: move the installed bundle or binary aside, rename the staged one into place. A running process keeps executing its open file, so the swap needs no exit first. A failed rename restores the original and reports.
    3. Hand off, with the old process, whose code is known to work, owning the outcome: rewrite the discovery file to mark the handoff (an additive `restarting` flag on the old process's own record, whose `pid` stays alive for the whole handoff, success or rollback (Step 7); older readers already tolerate unknown fields, `crates/gateway-api-discovery/src/file.rs`, lines 18 to 19), stop serving, drop the instance lease, and spawn the new binary with `--login`. The lease is a local `_instance_lease` in `crates/gateway/app/src/main.rs` (line 116), so the update module is handed it and drops it at the handoff (`GatewayInstanceLease`, `crates/gateway-api-discovery/src/lock.rs`, line 40: dropping its handle releases the OS lock, lines 34 to 38). The successor waits for nothing: the lease is already free, so it takes it at once.
       - `--login` matters because a process that loses the lease opens the running gateway's Settings page in the browser through `open::that` unless it was started with `--print-url` or `--login` (`main.rs`, lines 119 to 131). A successor that loses the lease to another new-version gateway, and any rollback-restored copy, must therefore open no browser.
    4. The mark is handled inside discovery resolution, so every reader picks it up. `Resolution` (`crates/gateway-api-discovery/src/stale.rs`, lines 21 to 30) is `#[non_exhaustive]` and gains `Restarting`. Both resolution paths validate the file and then remove one that fails, which would delete the mark at the first read: `resolve_named` (line 97), behind `resolve`, and `resolve_cancellable` (line 78), through `resolve_named_cancellable_with_effects` (lines 149 to 184). Both return `Restarting` for a marked file whose named old-process pid is alive and leave it in place, so readers wait through the whole handoff, including any rollback; a marked file whose old process is dead is stale as before. The read-only checks `is_running`, `is_live`, and `is_live_cancellable` (lines 202 to 233) treat a marked file as not live and not stale. Any process that holds the instance lease and resolves `Restarting` boots and replaces the file with its own record: holding the lease proves no other gateway is serving, so the mark needs no matching argument. This also covers a new-version gateway started by an older Workshop's supervisor or the login item.
       - Matchers. Inside the crate, `launch_or_attach` matches `Absent | Stale(_)` with no wildcard (`crates/gateway-api-discovery/src/lock.rs`, lines 155 and 236), so the compiler forces a choice there: it waits, never launches. Outside the crate every matcher uses a wildcard and would silently take the wrong branch, so each gains an explicit `Restarting` arm: `plan_gateway` (`crates/workshop/desktop/src/gateway/boot.rs`, line 125, `Ok(_)` falls through to `Launch`) waits for the file to resolve instead of launching; the supervisor re-check (`crates/workshop/desktop/src/gateway/supervisor.rs`, line 103, `Ok(_)` is `Missing`, which relaunches) waits; the launched-gateway probe (`crates/workshop/desktop/src/gateway/supervisor/launch.rs`, line 197) keeps waiting; `decide` (`crates/gateway/app/src/relaunch.rs`, line 71, `_ => Relaunch::Boot`) boots, since only a lease holder calls it; and `workshop-gateway`'s `resolve_with` (`crates/workshop/gateway/src/resolve.rs`, line 232, `_ => {}` falls back to the config endpoint) waits for the handoff instead.
       - `GatewayDiscoveryFile` (`crates/gateway-api-discovery/src/file.rs`, lines 20 to 34) has public fields, is not `#[non_exhaustive]`, and is built with struct literals in about 16 files (among them `crates/gateway/app/src/runner/thread.rs`, `diagnostics.rs`, `relaunch.rs`, and the desktop app's tests). The new field is `restarting: bool`, defaulted and omitted when false, and every full literal is updated (Step 7 lists the 13).
    5. The old process waits for any validated, unmarked gateway reporting the advertised version, not only one with the successor's pid: an older Workshop's supervisor or the login item may have started the installed path, which is already the new binary, and the successor then loses the lease and exits. On success it removes the moved-aside copy and exits.
    6. Only when no gateway at the new version appears before the timeout does the old process kill the successor if it is still running, restore the moved-aside copy, and spawn it with `--login`, keeping the mark in place. It waits for that restored gateway to publish its discovery file the same way, then exits; if that also times out it removes the mark, reports the failure in its log, and exits, leaving recovery to the next launch. A successor that panics or crashes during startup therefore never leaves a broken binary as the installed copy, and a successor that lost the lease to a healthy new-version gateway never causes a rollback over it.
    7. The successor does no rollback of its own. Losing the instance lease is not a boot failure: it takes the existing handoff path (`settle_gateway_startup`, `crates/gateway/app/src/relaunch.rs`, line 94).
  - Apply on Windows (no Workshop): download and verify the setup, start it detached with `/P /UPDATE`, and keep serving. The NSIS Gateway section finds the running gateway, stops it, and relaunches it because it stopped it (`GatewayWasRunning`, `crates/workshop/desktop/installer.nsi`, declared at line 87, detection at lines 795 to 803, relaunch through `nsis_tauri_utils::RunAsUser` with `--login` at lines 887 to 894); a gateway that exited first would not be relaunched.
  - Notice: a tray gateway checks at startup and every 24 hours, except on Windows with Workshop installed beside it, where Workshop's updater owns updates and shows its own notice, so the gateway runs no check and its `Update` item shows disabled, reading "Updates come from PromptForge Workshop" (Step 9). When an update exists, the tray status line and the `Update` item read "Update available: 0.N+1". It never applies an update on its own, because a restart drops loaded models and in-flight requests. Headless gateways (`--no-tray`, `gateway.service`) are manual server builds and update by rebuilding.
  - Triggers: the tray `Update` item checks and applies, with download progress in the tray status line; a `POST /update` route on the gateway does the same and answers before the handoff with the version it is moving to, or why it is not updating (current, Workshop-owned on Windows, verification failed, install location not writable). The route carries the same authority as `/shutdown` (`crates/gateway/app/src/admin/walled/shutdown.rs`, line 22, `RouteInfo::walled`). Walled routes are mounted behind `shared_loopback::require_loopback` (`crates/gateway/app/src/lib.rs`, lines 441 to 447) and take `LoopbackCaller` (`crates/gateway/app/src/auth.rs`, lines 130 to 154), so a LAN caller gets 403. `check_auth` (`auth.rs`, line 186) then accepts the bearer, the `/auth` handoff cookie, or, with `trust_loopback` on as the generated config sets it, a loopback caller with no credentials. Any local process can therefore call `POST /update`, as it can call `/shutdown`. That is safe because the route can only apply a newer version whose signature verifies against the embedded release key; the worst a caller can cause is the restart an update needs anyway.
  - Workshop's part: its update service calls `POST /update` on a local sidecar gateway after its own check, through a Tauri command, since workshop-server's gateway proxy refuses the route (Step 9), and never from a debug build, whether or not Workshop itself has an update, so a gateway behind Workshop is still updated. A 404 means the gateway predates self-update (for example a gateway from a nightly build before this change); the service records that and reports no error.
  - Supervisor: whatever started the update (the route, the tray item, a scheduled check), Workshop's supervisor gets `Resolution::Restarting` from its existing `resolve_cancellable` re-check (`crates/workshop/desktop/src/gateway/supervisor.rs`, lines 88 to 107) and waits for the file to resolve to a live gateway instead of launching one, with no timeout of its own while `Restarting` holds: `Restarting` lasts only while the old process is alive, and the old process's waits are bounded, so a supervisor timeout could only cut a rollback short and launch the installed path mid-restore. The supervisor and the successor therefore never race for the lease. An older Workshop resolves the marked file as stale, removes it, and launches the installed path, which is already the new binary; one of the two new-version processes wins the lease, and step 5 counts that as success.
- No-gateway boot failure: already covered. `boot_and_open` (`crates/workshop/desktop/src/main.rs`, lines 218 to 243) prints the error to stderr, shows it in a "PromptForge could not start" error dialog through `tauri-plugin-dialog`, and exits; the dialog shows `no_gateway_error`'s text, which this plan updates to name the per-platform location.
  - No migration path is needed for the gateway split: no copy installed today can update itself. No stable release exists, `workshop-latest/latest.json` returns 404, and nightly builds ship without updater artifacts (see Release Artifact Inventory).
- Releases: `v*` tags start a release. The first is `v0.3.1`: `v0.3.0` already exists as a tag (2026-09-08, commit `5edcb3c9`) with no release, so the workspace version bumps from 0.3.0 to 0.3.1 in the release commit and existing tags stay untouched. ## Decision Record

- Decisions:
  - Qt Installer Framework on macOS and Linux, NSIS kept on Windows. User's words: "go with Qt IFW on macOS and Linux". Rationale: one component tree and test shape for two platforms, with a maintenance tool for uninstall and component removal; NSIS already meets the requirements and drives the Windows updater. The maintenance tool of an offline installer adds or updates components only from a repository, which this plan does not publish, so it removes but never adds; adding Gateway later goes through Workshop's install offer. A rerun installer refuses a directory that holds an installation, so changing the selection means uninstalling with the maintenance tool, which keeps the profile, and running the installer again (Step 6). The remedy for adding STT later: name `[[stt_model]]` entries in the selected profile, then rerun the installer or `promptforge-gateway init`; `init` never rewrites an existing config, and fails when speech is requested and the profile declares none). IFW's record of installed versions drifts once the Tauri updater replaces the `.app` or AppImage; nothing reads those versions without a repository, and uninstall removes by path, so the drift is accepted. Qt IFW is GPL-3.0 with the Qt GPL Exception 1.0, which permits distributing its output under our terms.

  - A macOS user outside the admin group cannot write `/Applications/PromptForge`.   - Unsigned Qt IFW installers meet Gatekeeper's quarantine prompt, as today's unsigned DMG does.

- Removing the STT runtime when STT is deselected in Qt IFW's maintenance tool or the NSIS installer.
- Platform code signing and notarization for every installer.
